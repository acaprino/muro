# Design Options (hi-fi variations and tweak controls)

Gives the user alternatives inside one file: several distinct takes on a design, or one design with live controls. In the source's words: "one design is one bet; three let the user reject what they don't want and combine what they do." `<CD>` below stands for `<package_root>/scripts/claude-design-system-prompt/claude`.

## Behavior

0. **Read the originals whole before working, and scope by the selected intent.** The originals are the method, in the source's own words:
   - for `ui.design-variations`: `<CD>/skills/generate-variations.md`, all six phases;
   - for `ui.tweak-controls`: `<CD>/skills/make-tweakable.md`, all seven phases. Read it too when variations are presented through tweaks (step 5);
   - `<CD>/skills/discovery-questions.md`, for what to confirm with the user and how;
   - in `<CD>/system-prompt.md`, these chapters only, each from its heading to the next `# ` heading: `# 3. Asking questions first`, `# 4. Rooting designs in existing context`, `# 14. Respecting the medium`, `# 15. Understanding users`, `# 16. Quality over quantity`, `# 17. Output principles`, `# 19. IP and content boundaries`. Chapter 17 sends to chapter 8 for the minimum sizes (of `# 8. Typography system` read only the section `## Scale rules per medium`) and chapter 19 sends to `# 5. Content principles — no filler`: read them for those references. No other part of the prompt is read for this capability.

   The steps below are an index into those files. Where this body and an original differ, the original wins, except for the changes listed in the Sources section under "Changes for coexistence". Variations are steps 1 to 5, tweak controls steps 6 to 9; record what was not asked as `not requested`. The design to work on is the user's file, or a recorded `prototype_file`.
1. **Establish the baseline** (generate-variations Phase 1). "Confirm: **what is being varied** (screen, component, flow, visual treatment — scope determines how many variations are useful); **existing design context** (variations should root in the UI kit / design system unless explicitly asked to break free); **number** (default 3; 5–6 is a healthy ceiling); **axis preference** (visuals, interactions, layout, or copy/tone — where does the user want exploration weighted?)." The existing context is the recorded `aesthetic_direction`, `design_tokens`, `palette` and `typography`, or the product's own files, read as chapter 4 says.
2. **Pick the axes** (Phase 2). "Pick 2–4 dimensions to vary across", from the skill's list. "Write down which axis each variation flexes — it makes the comparison legible to the user."
3. **Build with intent, basic to bold** (Phases 3 and 4). "**Specify each variation concretely before building it** — distinct palette family, distinct type pairing, distinct layout skeleton, written down per variation. Variety must be designed, not hoped for". "Order from most by-the-book to most novel": By the book, Refined, Novel, then "4–6 (if requested)", each as the skill defines it. "**Cover both ends.** All-safe wastes the user's time; all-wild ignores the brief." "For the novel variation, deliberately pick something off-distribution and interesting."
4. **Vary substantively, not cosmetically** (Phase 4). "Variations should differ in layout, hierarchy, what's primary, type system, density, interaction approach, or copy strategy — not just button color, accent shade, or shadow opacity. If two are too close, drop one for a more substantive alternative. The user should be able to articulate the difference between any two variations in one sentence."
5. **Present in a single file, annotate and recommend** (Phases 5 and 6). Static variations side by side in one labelled grid, "or **tweaks** ... if the variations share structure and differ on a few axes" (steps 6 to 9). "For flows, build each variation as a small storyboard". "Caption each variation in one or two sentences". "End with a clear recommendation — the user decides, but a designer offers an opinion ... Don't hedge that all options are equally good; they aren't." Then name the next step the skill lists: a refinement round, another variation round on a different axis, a prototype, or a review before shipping.
6. **Identify what should be tweakable** (make-tweakable Phase 1). "Confirm with the user — or propose and check — which aspects to expose: color (primary, accent, background tone), typography (family, base size, scale ratio), density (tight / normal / loose), layout variant, component variants (filled/ghost buttons, card treatment), copy (headline, subhead, CTA text), feature flags (show/hide sections)." "**Keep the tweak surface small** — 3–8 controls. A few meaningful axes to explore, not a Figma clone. If the user didn't ask for tweaks but the design has obvious axes of variation, add 1–2 by default to surface interesting possibilities."
7. **Design the panel** (Phase 2). "The panel lives inside the prototype, floating (typically bottom-right), semi-transparent with a subtle border, titled **"Tweaks"**". "Use the right control per value type: color picker for colors; dropdown or button group for fonts and variants; slider with sensible min/max for numbers; toggle for booleans; text input for copy. Keep controls compact — a narrow stacked column beats a sprawling panel."
8. **Wire the live updates and persist** (Phase 3, chapter 14). "Use CSS custom properties for visual tokens so everything referencing them updates"; "For non-CSS values (copy, layout variants, feature flags), use JS state with re-render or DOM manipulation." Defaults live in one valid JSON object in an inline script of the file; changed values are saved to `localStorage` and restored on load (see Specifics for the source's host protocol).
9. **Hide the controls when off, verify and summarize** (Phases 6 and 7). With the panel off, "the panel is entirely hidden — not dimmed, not collapsed to a corner. This is non-negotiable: any visible edit-mode chrome makes the design look unfinished." State how it opens (a key, or a parameter in the address). Verify as Phase 7 lists: turn the panel on and off; "change each tweak and confirm it updates live; reload and confirm values persist; check the design reads as a finished artifact with the panel off."
10. **Record** `options_file` and `options_summary`: the variations with their axes, captions and the recommendation; or, as the skill's summary asks, "tweaks exposed and their value types, defaults, tweaks considered but excluded (and why), whether the set covers the user's exploration axes."

## Specifics

- **One file, many variants.** "**Do not produce v1.html / v2.html / v3.html** — one file, all variations visible or toggle-able."
- The source's panel is switched by a toolbar of its own host, through window messages and a marked defaults block that the host rewrites on disk (`<CD>/skills/make-tweakable.md`, Phases 4 and 5). No host this package runs on has that toolbar, so the panel here opens by itself and persists in the browser. Follow those two phases only inside a host that provides the toolbar.
- The source's side-by-side canvas starter (`design_canvas.jsx`) is not packaged: use a plain CSS grid.
- A recorded direction stays the owner of the look. A variation that leaves it is labelled as doing so, and a control never writes outside the file it lives in.
- Chapter 19: "If asked to recreate a company's distinctive UI patterns, proprietary command structures, or branded visual elements, refuse", unless the user states the product is their own. Such a design is not offered as a variation.
- Nothing is installed.

## Checks

- **options_differ_in_one_sentence**: for any two variations the difference is stated in one sentence and is not cosmetic; not applicable to a tweak-only request.
- **both_ends_covered**: the set holds a by-the-book variation and a novel one.
- **single_file_delivered**: every variation or control is in one file.
- **recommendation_given**: one variation is recommended with its reason.
- **tweaks_update_and_persist**: each control changes the design live and its value survives a reload; without a browser this is not tested and said so.
- **panel_hidden_when_off**: with the panel off it is entirely hidden, not dimmed and not collapsed to a corner, and the way to open it is stated.
