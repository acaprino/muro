# UI Prototype (interactive, hi-fi)

Builds a prototype that behaves. In the skill's words: "**Prototypes interact** — static screenshots strung together with `<a>` tags don't count; the point is to test the flow with real clicking, typing, validating, succeeding, failing." `<CD>` below stands for `<package_root>/scripts/claude-design-system-prompt/claude`.

## Behavior

0. **Read the originals whole before working.** They are the method, in the source's own words:
   - `<CD>/skills/make-a-prototype.md`, all seven phases;
   - `<CD>/skills/discovery-questions.md`, for the question round of step 1;
   - in `<CD>/system-prompt.md`, these chapters only, each from its heading to the next `# ` heading: `# 2. Workflow`, `# 3. Asking questions first`, `# 4. Rooting designs in existing context`, `# 5. Content principles — no filler`, `# 10. Accessibility and inclusivity`, `# 11. Interaction and feedback`, `# 12. Simplicity and one clear CTA`, `# 14. Respecting the medium`, `# 15. Understanding users`, `# 16. Quality over quantity`, `# 17. Output principles`, `# 18. Collaboration and delivery`, `# 19. IP and content boundaries`. Chapter 17 sends to chapter 8 for the minimum sizes: of `# 8. Typography system` read only the section `## Scale rules per medium`. No other part of the prompt is read for this capability.

   The steps below are an index into those files. Where this body and an original differ, the original wins, except for the changes listed in the Sources section under "Changes for coexistence".
1. **Discovery, in one round** (skill Phase 1, discovery-questions, chapters 3 and 15). Read what is attached first. "Confirm before building: **the flow** (screens, entry point, goal state — map it as a list); **fidelity** (hi-fi or mid-fi); **device frame** (desktop browser, iOS, Android, macOS window); **variations** (one flow or several to compare); **brand / design system** (always confirm ...); **sample data** (real-looking content, no Lorem ipsum)." Minor choices are decided and listed in the summary, as discovery-questions Phase 2 says.
2. **Take the look from what exists** (chapter 4). Use the recorded `aesthetic_direction`, `design_tokens` and `component_inventory`, or `palette`, `typography` and `constraints` from a website step; otherwise the product's own files: "**read the source — don't rely on memory.** Open the theme file, the tokens, the component you're modifying. Lift exact hex codes, spacing values, and font stacks." A recorded `wireframe_decision` is the structural brief. A hi-fi prototype with nothing to match should have reached this step after `aesthetic-direction` (see `needs`); if it did not, report that and do as chapter 4 says: "If you cannot find context, **ask the user for it.** Do not invent a brand or visual language out of thin air unless explicitly asked to".
3. **Map screens and state** (skill Phase 2). "Write the flow down before building, and drop it into the file as a comment block so the user can see the plan", in the form of the skill's example (screens with their actions and targets, then the state variables).
4. **Build screen by screen** (skill Phase 3, chapters 2, 12 and 18), showing the file "as soon as there's a skeleton". "For each screen: mount it in the DOM (display toggling or React state within a single page); hi-fi visuals matching the design system — real components, not generic boxes; plausible real content (actual names, product copy, numbers); one primary CTA per screen, secondary actions smaller and de-emphasized."
5. **Wire up interactions** (skill Phase 4, chapter 11). "Every interaction wired, not just the happy path": Navigation, Form validation, Loading states, Success and error feedback, State changes, each as the skill's bullet states it. "Fake the latency with `setTimeout` — don't skip the loading state because the work is fake; it's part of what's being tested."
6. **Sub-state and persistence** (skill Phase 5, chapter 14). "Make meaningful sub-state reactive: selection state, filter/sort state, modal/dropdown open-state (focus moves into the modal, Escape closes it), form values and errors." "Persist what matters across reload via `localStorage`: current screen, form drafts, tweak values".
7. **Verify** (skill Phase 6, chapter 18). "Walk the full flow in the preview: every CTA leads somewhere, every form validates, every error is clear and recoverable, every async action shows feedback, every state change is visible, keyboard navigation works (Tab through, Enter to submit, Escape to close), focus is visible." Also reload once and confirm the state of step 6 returns. Give the check to a verifying agent when the host has one. "If you can't verify a behavior, say so in the summary rather than claiming success."
8. **Record** `prototype_plan`, `prototype_file` and `prototype_verification`, and "Summarize briefly: what flows work, what's faked (e.g., "submit calls a setTimeout fake"), what's open for the user to decide." Chapter 18: "summarize **caveats and next steps only**."

## Specifics

- **No filler** (chapter 5, chapter 19). "**Every element must earn its place.**" What counts as filler and the five-question test are chapter 5's. "If a section feels empty, that is a layout problem, not a content problem. Solve it with composition, not invention." "If you think additional sections, copy, or content would improve the design, **ask the user first.**"
- **Semantic and reachable** (chapter 10): its sections on semantic HTML, keyboard navigation, screen reader support, motion and form design apply as written, with "**Never remove the focus ring.**" Chapter 8, `## Scale rules per medium`: "**Mobile interfaces:** body text never smaller than 16px", "**Interactive hit targets:** never smaller than 44px × 44px", "**Desktop interfaces:** 14–16px body is standard".
- **Timings.** Chapter 11: "Smooth transitions on state changes — **0.2–0.3 seconds**, ease curve". A recorded `motion-spec` and `reduced-motion` come first when the plan has them.
- **Device frame.** The skill copies `ios_frame.jsx`, `android_frame.jsx`, `macos_window.jsx` or `browser_window.jsx` from starters of its own host, which are not packaged: draw a plain frame in CSS, or none, and say so. "The frame stays fixed; the prototype lives inside it."
- **Variations, if requested** (skill Phase 7). Side by side in a plain CSS grid or as in-prototype toggles, in the same file: "**Don't scatter v1.html / v2.html / v3.html across the project — one file, many variants.**" A floating tweak panel is the `design-options` step.
- Chapter 19: "If asked to recreate a company's distinctive UI patterns, proprietary command structures, or branded visual elements, refuse", unless the user states the product is their own. "Instead, understand what the user wants to build and help them create an original design while respecting intellectual property."
- Nothing is installed. When the file loads a library or a font from the network, say so.

## Checks

- **flow_and_state_mapped_first**: the file holds the screen and state map as a comment block, written before the screens were built.
- **design_context_matched**: colours, type, spacing and components trace to the recorded direction, the tokens or the product's own files; nothing was invented beside an existing system.
- **every_interaction_wired**: navigation, form validation, loading states, success and error feedback and state changes are wired as the skill's Phase 4 lists them, not only the happy path.
- **state_survives_reload**: after a reload the prototype is on the same screen with its form drafts, and with its tweak values when it has any.
- **no_filler_or_invented_content**: no Lorem ipsum, made-up statistics, buttons with no destination, redundant or unrequested sections remain.
- **unverified_behavior_disclosed**: every behaviour that could not be verified is named in the summary as not tested.
