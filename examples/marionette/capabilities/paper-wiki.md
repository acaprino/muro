# Paper Wiki

Maintains an Open Knowledge Format (OKF) paper wiki as Markdown files with YAML frontmatter. `<PW>` is `<package_root>/scripts/open-paper-skills/skills/paper-wiki-manager`; `$PS` is `<package_root>/scripts/open-paper-skills/skills/paper-search/scripts/paper_search.py`.

## Behavior

0. **Read the original first.** Read `<PW>/SKILL.source.md` whole before working. It is the method in the source's own words. Where this body and that file differ, the file wins, except for the changes listed in the Sources section below under "Changes for coexistence". The paths it names (`references/...`, `assets/...`, `scripts/...`) are under `<PW>`. Read with it, when the source says so: `<PW>/references/repeated-ingestion.md` whole when the paper page already exists; `<PW>/references/schema.md` (the "stricter paper-wiki profile") for the frontmatter and body of the page type you write; `<PW>/references/SPEC.md` is "the bundled OKF format snapshot". The steps below are an index into the source's "Workflow"; sentences in quotation marks are the source's.
1. **Locate the wiki** (source "Scope"). "Use `paper-wiki/` as the default wiki root unless the user names a different path." "The four canonical page collections are `papers/` (one page per arXiv paper), `topics/` (thematic synthesis pages), `concepts/` (entity pages for named methods, datasets, benchmarks, metrics, terms, and tools), and `sources/` (non-paper reading — blogs, docs, talks — as `type: Reference`). `papers_zh/` stores `zh-CN` mirrors of canonical paper notes and does not participate in indexes, topic/concept backlink requirements, or graph nodes and edges."
2. **Resolve the paper** (source "Workflow" 1 and "Fetching Papers", Input resolution). "Parse the arXiv ID from the URL, user input, or PDF filename/path. For a PDF, check the filename first (e.g., `2401.00001.pdf`); if the ID is not in the filename, extract it from the PDF header or `arxiv.org` URL embedded in the document." For a title or description only: "run `uv run $PS search "TITLE" --mode keyword --limit 5`. Proceed without asking only when exactly one candidate's title equals the given title once case and punctuation are ignored, and name that candidate in your reply. Otherwise show the top candidates to the user and wait for confirmation before proceeding; never guess the ID." Use `literature_findings` when it is recorded: a paper a search step already returned needs no second search.
3. **Existing page first** (source "Workflow" 2). "Read the existing paper file if `paper-wiki/papers/<arxiv_id>.md` already exists. If it exists, read and follow [`references/repeated-ingestion.md`](references/repeated-ingestion.md) before editing; never append a second generated note or template wholesale." "For every repeated paper input, treat the existing canonical body as the current best synthesis. Merge only evidence-supported changes into its existing sections, protect human-owned notes, and use the no-op and review gates" of that file.
4. **Fetch** (source "Fetching Papers"). "A source switched off there stays off on every route, including web fetches and MCP connectors; when the note needs one, say so and let the human decide." "run `uv run $PS fetch ARXIV_ID`. It writes the full text from the first source in the read order that returns a complete text to the file its JSON report names, and fills `metadata` (title, authors, date, abstract) from arXiv, else Hugging Face. Read the file as the primary source for the paper body summary; distil it into the configured body sections rather than reproducing it. Cite the report's `source` and `url` under `# Citations`, and note in the body which source the text came from. On exit 1, no source returned a complete text: report the `tried` outcomes and the `pdf` link to the user rather than fetching through another route." "Prefer arXiv for bibliographic facts; use project pages, GitHub, Hugging Face paper pages, or Semantic Scholar only as additional sources, and only through a source the human has switched on."
5. **Write the paper page** (source "Workflow" 3 and 5, "Paper Documents", "Metadata Rules"). "Use `assets/paper-wiki.toml` as the default paper body configuration for this skill. When reading the config, enumerate all `paper_body.profiles` entries. Use `paper_body.default_profile` by default, but choose another configured profile when the user requests it or when the paper type clearly matches it. Use the selected `paper_body.profiles.<name>.sections` list for new paper bodies. Treat `paper_body.required_sections` as validation requirements only when the user configures them." "Use `paper_body.section_descriptions` as drafting guidance for what each section should contain. Do not copy those descriptions into generated paper notes unless the user explicitly asks for visible prompts." "Write `status: unread` on every new paper and source, including ones an agent read in full".
6. **Fidelity pass** (source "Paper Documents"). "Before finalizing a drafted note, run a **fidelity pass**: locate every load-bearing number, taxonomy branch, named exemplar, and comparative claim in the retrieved full paper or an additional source listed under `# Citations`. Mark reader-constructed examples and inferences explicitly, distinguish the source's qualitative synthesis from comparable empirical evidence, and remove claims that cannot be traced to a used source. The pass is complete only when every such claim has an identified source and the note's evidence boundaries match what that source can establish." "the structural validator cannot verify factual faithfulness to the paper."
7. **Chinese mirror** (source "Workflow" 7 and "Chinese Paper Notes"). "Read `[localized_notes].enabled` in `assets/paper-wiki.toml`. When true, create or update the `zh-CN` mirror under `paper-wiki/papers_zh/<arxiv_id>.md` following Chinese Paper Notes." The packaged file has it true. "A Chinese mirror is an auxiliary reading artifact and must not be added to `papers/index.md`, topic or concept `# Papers` sections, or `viz.html` as a node or edge."
8. **Topics and concepts** (source "Workflow" 8 to 10, "Topic Documents", "Concept Documents"). "Identify and update 1 to 3 important themes following Topic Documents." "Important themes usually satisfy at least two of these conditions", listed there. "Do not create a topic for every tag." "Prefer reusing an existing topic when the new theme is semantically equivalent to one already present." "Every topic page should include `# Scope`, `# Papers`, and `# Open Questions`." "Create a concept page when a named entity satisfies at least one of": "Two or more papers in the wiki reference it", "It is a durable, field-level entity likely to recur in future reading", "The user asks to track it." "Do not create a concept page for a method that only its own paper describes". "Ensure links are bidirectional".
9. **Sources, project links, indexes** (source "Source Documents", "Project Links", "Indexes", "Workflow" 11 and 12). "When the input is a non-paper source (a blog post, documentation page, or talk) with no arXiv ID, add it under `paper-wiki/sources/<slug>.md` instead of `papers/`. Fetch it with a web request (`paper-search fetch` does not apply)." Its links to topics and concepts "are **one-way**". "If the paper is used by a project in this repository, add or update the paper's `# Used In Projects` section following Project Links." "Update `paper-wiki/papers/index.md`, `paper-wiki/topics/index.md`, `paper-wiki/concepts/index.md` (when concepts exist), and every affected topic or concept page; update the wiki home `paper-wiki/index.md` if a new canonical collection appeared. Do not create a `papers_zh/index.md` entry."
10. **Finish** (source "Finishing Commands", with its list of checks). Fetch the viewer libraries if missing (Specifics), then "Run bundled scripts from this skill's root directory", which is `<PW>`: "Pass the wiki root as an absolute path when the target repo is not the current working directory. Generate `viz.html` before validation because the validator reads the generated graph file."
    `uv run scripts/generate_viz.py /absolute/path/to/paper-wiki` and `uv run scripts/validate_paper_wiki.py /absolute/path/to/paper-wiki`. "If `uv` is unavailable or blocked by sandbox/cache access and the environment already has Python 3.11+, run the scripts directly with `python`". "Use `--config <path/to/paper-wiki.toml>` only for a temporary validation profile or another repo layout." A repeated ingestion that ends `no-op` changes no file and does not regenerate `viz.html` (`<PW>/references/repeated-ingestion.md`, "Decision Flow" 4).
11. **Other requests.**
    - Reading status (source "Metadata Rules"): "`status` is the human's reading state — `unread`, `skimmed`, or `read` — and changes on the human's word alone." When the user asks, "run `scripts/set_status.py <papers/ID | sources/slug> <status> --root <wiki-root>`, which rewrites only that frontmatter line." The script's header adds: "Regenerate viz.html afterwards so the embedded graph picks up the change."
    - Custom note template (source "Custom Paper Body Profiles"): "treat it as a custom `paper_body.profiles.<name>` profile, not a change to the OKF contract. Use `scripts/create_paper_body_profile.py` as the profile-generation interface." "By default, the script saves the finished profile to this skill's bundled `assets/paper-wiki.toml` so it is reusable in later paper-wiki tasks", here `<PW>/assets/paper-wiki.toml`, a file every new release of this package replaces: tell the user so, and use the wiki-specific config below for a profile that must outlive an upgrade; `--preview` prints the TOML "without changing the config". "Do not change `paper_body.default_profile` after creating a custom template unless the user explicitly asks to make that template the default. If asked, rerun the script with `--set-default` for the intended profile." "For a wiki-specific template, write to a separate config and pass it to validation with `--config <path/to/paper-wiki.toml>`."
    - Comparison (source "Comparison Tasks"): "When comparing papers, write the comparison as a separate note only if the user asks for a durable artifact. Otherwise answer in chat and reference the paper files. Compare along concrete axes such as problem framing, method, evidence, assumptions, failure modes, reusable artifacts, and relevance to the user's research direction."
    - Viewer (source "Visualization"): "`paper-wiki/viz.html` is required." "regenerating `viz.html` is all that is needed to pick up viewer changes; no per-paper edits are involved."

## Output handoff

Resolve `<package_root>` with the `package_root` returned beside these instructions, never against the consumer project. Return `wiki_changes` (pages created or updated, with paths, and the sources actually used; for a repeated ingestion, the four items of the source's "Result Report") and `wiki_validation` (the validator's result and whether `viz.html` was regenerated; for a `no-op`, or a `needs-review` that changed no file, that nothing was regenerated or validated and why) as JSON strings. For a mapped step, submit them through the coordinator's `record` command with the step's `map_id` and `capability`. Do not edit `<state_dir>/map.md` or `<state_dir>/state.json`; the coordinator is their only writer.

## Specifics

- "Preserve these user-curated fields when updating a paper": "`status`", "`priority`", "`tags`", "`# Notes`", "`# 个人笔记`", "any custom frontmatter keys not defined in `references/schema.md`". "Preserve existing paper body layout when updating a paper unless the user explicitly asks to reorganize it."
- "Cite only sources that were actually used."
- Runtime dependency, viewer libraries: `generate_viz.py` inlines five MIT libraries from `<PW>/scripts/vendor/`, which this package does not redistribute. When one is missing, download the exact versions listed in `<PW>/scripts/vendor/README.md` from the jsDelivr npm mirror into that folder, under the file names of its table (cytoscape 3.28.1, layout-base 2.0.1, cose-base 2.2.0, cytoscape-fcose 2.2.0, marked 12.0.0; about 700 KB) and say so in one line. "keep all five and load them in the order listed above." If the download fails, the notes stand and viewer and validation are reported as not done.
- Runtime dependency: `uv`, or Python 3.11+ already present, as in `paper-search`.

## Checks

- **fidelity_pass_done**: every load-bearing number and comparative claim in a new or changed note was located in the fetched paper or a cited source; inferences are marked.
- **links_bidirectional_and_indexed**: each paper-topic and paper-concept link exists on both pages and every new page is in its index.
- **viewer_regenerated_before_validation**: `generate_viz.py` ran after the last content edit and before the validator.
- **validator_passes**: `validate_paper_wiki.py` exits clean on the wiki root; quote its final line.
- **reading_status_left_to_user**: no `status` changed without the user's instruction, and new pages are `unread`.
