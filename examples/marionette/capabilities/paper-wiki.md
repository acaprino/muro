# Paper Wiki

Maintains an Open Knowledge Format (OKF) paper wiki as Markdown files with YAML frontmatter. `<PW>` is `<package_root>/scripts/open-paper-skills/skills/paper-wiki-manager`; `$PS` is `<package_root>/scripts/open-paper-skills/skills/paper-search/scripts/paper_search.py`. The packaged original `<PW>/SKILL.source.md` is the full version of this method and wins where this body differs from it, except for the changes listed in the Sources section; the paths it names (`references/`, `assets/`, `scripts/`) are under `<PW>`. Open the sections and files named below when the task reaches them.

## Behavior

1. **Locate the wiki.** The root is `paper-wiki/` unless the user names another path. Collections: `papers/` (one page per arXiv paper), `topics/`, `concepts/` (named methods, datasets, benchmarks, metrics, terms, tools) and `sources/` (non-paper reading, `type: Reference`). `papers_zh/` holds `zh-CN` mirrors and takes no part in indexes, backlink requirements or graph nodes and edges. For the frontmatter and body of the page type you write, open its section of `<PW>/references/schema.md`; where that file is silent on a format question, `<PW>/references/SPEC.md` (the bundled OKF snapshot) decides.
2. **Resolve the paper.** Take the arXiv ID from the URL, the user's input or the PDF file name; if the name has none, from the PDF header or an embedded `arxiv.org` URL. With only a title or description, run `uv run $PS search "TITLE" --mode keyword --limit 5`: proceed without asking only when exactly one candidate's title equals the given title once case and punctuation are ignored, and name that candidate in the reply; otherwise show the top candidates and wait for confirmation. Never guess the ID. When `literature_findings` is recorded, a paper it already returned needs no second search.
3. **Existing page first.** If `papers/<arxiv_id>.md` exists, read `<PW>/references/repeated-ingestion.md` and follow it before editing: the existing body is the current best synthesis, only evidence-supported changes merge into its existing sections, human-owned notes are protected, and its `no-op` and `needs-review` gates apply. Never append a second generated note or template wholesale.
4. **Fetch.** `uv run $PS fetch ARXIV_ID` writes the full text from the first source in the read order that returns a complete text to the file its JSON report names, and fills `metadata` from arXiv, else Hugging Face. That file is the primary source for the note: distil it, do not reproduce it. Cite the report's `source` and `url` under `# Citations` and note in the body which source the text came from. On exit 1 report the `tried` outcomes and the `pdf` link to the user; do not fetch through another route. A source switched off in `memory/paper-sources.json` stays off on every route, web fetches and MCP connectors included: when the note needs one, say so and let the user decide. Prefer arXiv for bibliographic facts; project pages, GitHub, Hugging Face paper pages or Semantic Scholar are additional sources only, and only through a source that is on.
5. **Write the paper page** under `papers/`. Read `<PW>/assets/paper-wiki.toml` and enumerate all `paper_body.profiles`. Use `paper_body.default_profile` unless the user requests another profile or the paper type clearly matches one, and take that profile's `sections` list for a new body. `paper_body.section_descriptions` guide the drafting and are not copied into the note unless the user asks for visible prompts; `paper_body.required_sections` are validation requirements only when the user configures them. Write `status: unread` on every new paper and source, including ones you read in full. The remaining drafting rules are in the original's "Paper Documents".
6. **Fidelity pass.** Before finalizing a drafted note, locate every load-bearing number, taxonomy branch, named exemplar and comparative claim in the retrieved full paper or in an additional source listed under `# Citations`. Mark reader-constructed examples and inferences explicitly, distinguish the source's qualitative synthesis from comparable empirical evidence, and remove claims that cannot be traced to a used source. The pass is complete only when every such claim has an identified source and the note's evidence boundaries match what that source can establish. The validator checks structure, not faithfulness.
7. **Chinese mirror.** Read `[localized_notes].enabled` in the config (the packaged file has it true). When true, create or update `papers_zh/<arxiv_id>.md` after the English note, following the original's "Chinese Paper Notes" (frontmatter, translation rules). The mirror is never added to `papers/index.md`, to a topic's or concept's `# Papers`, or to the graph as a node or edge.
8. **Topics and concepts.** Identify and update 1 to 3 important themes; the original's "Topic Documents" lists the conditions, of which an important theme usually meets at least two. Do not create a topic for every tag, and prefer reusing an existing topic that is semantically equivalent. A topic page has `# Scope`, `# Papers` and `# Open Questions`. Create a concept page when a named entity meets at least one of: two or more papers in the wiki reference it; it is a durable field-level entity likely to recur; the user asks to track it. Do not create one for a method only its own paper describes. Page types and sections are in "Concept Documents". Links are bidirectional: the paper links to each topic and concept, and each lists the paper under `# Papers`.
9. **Sources, project links, indexes.** A blog post, documentation page or talk with no arXiv ID goes under `sources/<slug>.md`, fetched with a web request (`fetch` does not apply), as the original's "Source Documents" says; its links to topics and concepts are one-way. If a project in the repository uses the paper, add or update `# Used In Projects` following "Project Links". Update `papers/index.md`, `topics/index.md`, `concepts/index.md` (when concepts exist), every affected topic or concept page, and the wiki home `index.md` when a new canonical collection appeared ("Indexes"); never index `papers_zh/`.
10. **Finish.** Go through the check list in the original's "Finishing Commands". Fetch the viewer libraries if missing (Specifics). Then, from `<PW>` and with the wiki root as an absolute path, generate the viewer before validating, because the validator reads the generated graph file: `uv run scripts/generate_viz.py /absolute/path/to/paper-wiki`, then `uv run scripts/validate_paper_wiki.py /absolute/path/to/paper-wiki`. If `uv` is unavailable or blocked by sandbox or cache access and Python 3.11+ is already there, run the two scripts with `python`. `--config <path/to/paper-wiki.toml>` is only for a temporary validation profile or another repo layout. A repeated ingestion that ends `no-op` changes no file and runs none of this.
11. **Other requests.**
    - Reading status: `status` (`unread`, `skimmed`, `read`) is the user's reading state and changes on the user's word alone. When asked, run `scripts/set_status.py <papers/ID | sources/slug> <status> --root <wiki-root>`, which rewrites only that frontmatter line, then regenerate `viz.html`.
    - Custom note template: it is a `paper_body.profiles.<name>` profile, not a change to the OKF contract, made with `scripts/create_paper_body_profile.py` as the original's "Custom Paper Body Profiles" shows (`--preview` prints the TOML without saving). By default the script saves to `<PW>/assets/paper-wiki.toml`. A profile saved in the bundled config is replaced by the next release of the package: tell the user, and for a profile that must last write a separate wiki-specific config and pass it to validation with `--config`. Do not change `paper_body.default_profile` unless the user explicitly asks; then rerun with `--set-default`.
    - Comparison: write a separate note only when the user asks for a durable artifact; otherwise answer in chat and reference the paper files. The axes are in the original's "Comparison Tasks".
    - Viewer: `viz.html` is required; regenerating it is all that viewer changes need. Open the original's "Visualization" when the user asks how the Graph and Timeline tabs behave.

## Output handoff

Resolve `<package_root>` with the `package_root` returned beside these instructions, never against the consumer project. Return `wiki_changes` (pages created or updated, with paths, and the sources actually used; for a repeated ingestion, the four items of "Result Report" in `<PW>/references/repeated-ingestion.md`) and `wiki_validation` (the validator's result and whether `viz.html` was regenerated; for a `no-op`, or a `needs-review` that changed no file, that nothing was regenerated or validated and why) as JSON strings. For a mapped step, submit them through the coordinator's `record` command with the step's `map_id` and `capability`. Do not edit `<state_dir>/map.md` or `<state_dir>/state.json`; the coordinator is their only writer.

## Specifics

- When updating a paper, preserve the user-curated fields: `status`, `priority`, `tags`, `# Notes`, `# 个人笔记` and any custom frontmatter key not defined in `references/schema.md`. Preserve the existing body layout unless the user explicitly asks to reorganize it.
- Cite only sources that were actually used.
- Runtime dependency, viewer libraries: `generate_viz.py` inlines five MIT libraries from `<PW>/scripts/vendor/`, which this package does not redistribute. When one is missing, download the exact versions and file names listed in `<PW>/scripts/vendor/README.md` from the jsDelivr npm mirror into that folder (about 700 KB) and say so in one line; keep all five. If the download fails, the notes stand and viewer and validation are reported as not done.
- Runtime dependency: `uv`, or Python 3.11+ already present, as in `paper-search`.

## Checks

- **fidelity_pass_done**: every load-bearing number and comparative claim in a new or changed note was located in the fetched paper or a cited source; inferences are marked.
- **links_bidirectional_and_indexed**: each paper-topic and paper-concept link exists on both pages and every new page is in its index.
- **viewer_regenerated_before_validation**: `generate_viz.py` ran after the last content edit and before the validator.
- **validator_passes**: `validate_paper_wiki.py` exits clean on the wiki root; quote its final line.
- **reading_status_left_to_user**: no `status` changed without the user's instruction, and new pages are `unread`.
