# Design File (brief and DESIGN.md)

Records a developer's design selections where every later session can read them: a design brief, then the project's `DESIGN.md`, with values in YAML front matter and their functions in the body. It records selections and imposes no visual style. `<ZS>` below stands for `<package_root>/scripts/zero-slop-design`. The packaged originals are the full version: an original wins where this body differs, except for the changes listed in the Sources section: the skill file `<ZS>/skills/<name>/SKILL.source.md` named in each step, `<ZS>/references/procedure.md` and `<ZS>/references/design-format.md` (both govern every step here), `<ZS>/spec/zsd-design-md.md` (the full profile, with its rule numbers) and `<ZS>/templates/DESIGN.md` (the format example).

## Behavior

Record the output that was not asked for as `not requested`.

1. **Before the task** (`procedure.md`): read the project instructions, find the target repository and paths, read the design file and any design brief, record the task area and the developer's selections, and keep project components and assets when applicable. If different instructions prevent the same task, get a developer decision. Record missing data as `unresolved` and give example values the status `proposed`. The template is example data and does not set the developer's selections. Interface text comes from the developer's instructions.
2. **Brief** (`define-design`): get the audience and primary task from the developer or the project data; record the approved references and their applicable functions, the selections to keep and the selections to prevent; compare the selections for differences that prevent the same task and get a developer decision for each; record missing data as `unresolved` and put example values in a different list with the status `proposed`; write the brief at the specified project path and show the recorded selections and missing data.
3. **Create** (`create-design-md`): from the brief or the developer's instructions, find the target design file and the project token source and keep applicable tokens and components from the project. Use the template as the format example and replace its example selections with source data; values go in YAML, their functions in the body. Record the source method and source locations, record example or missing selections in `x-zsd.unresolved`, set `x-zsd.kind` to `project` and `x-zsd.review.status` to `draft`, write the target file, then step 6.
4. **Extract** (`extract-design`): record source paths or URLs and the source date; find colors, typography, spacing, shapes, components and states in the source data, with computed styles when an interface is available; compare items of the same type before making a token; record each source location with its item; mark image measured data as estimates and never show an estimate as a measured value; record the interface states and responsive conditions the source does not show as `unresolved`; map the data to the design format, set the source method to `generated` or `hybrid`, write the target file, then step 6.
5. **Update** (`update-design-md`): record the design data before the change; find related tokens, body instructions and applicable modes; get a developer decision if the new instructions differ from selections to keep; change the specified values and their related instructions and keep every other selection; change source data and unresolved items; set the review status to `draft`; do step 6, compare the file with the recorded data (`node <ZS>/tools/zsd.mjs diff <before> <after> --json` compares YAML data) and show the changed paths and the related interface work. To set one area in depth, open that area's skill file, follow its numbered procedure and change only that area's data and related instructions:
   - `define-typography`: tokens for headline, body and label roles; each font source and its fallback family; font size, font weight as a number, unitless line height, `letterSpacing` when the target format is DTCG; text wrapping, long content and content language conditions; font states the available assets do not supply.
   - `define-color-system`: role tokens for surfaces, text, interface actions and status indicators; the necessary primary and surface pairs; each foreground and background pair, with contrast measured for opaque pairs and alpha colors measured against the surface in operation; a text or shape status indicator with each status color; mode overrides with the same color keys; hover, focus, error and disabled states examined.
   - `define-responsive-layout`: content sequence and primary actions; content limits and spacing tokens; breakpoint tokens at the widths where the content needs a different layout; navigation, column and container behavior at each; long text, empty content and large data; the same reading and keyboard sequence; necessary horizontal scrolling recorded.
   - `define-interaction-states`: the applicable default, hover, focus, pressed, selected and disabled states and the applicable loading, empty, error and success states; each trigger, result the user can see and recovery step; keyboard operation and focus movement; a condition that prevents the same submission again when applicable; motion tokens and reduced-motion behavior; project components for applicable states; states that are not applicable marked with their conditions.
6. **Document checks** (`procedure.md`): run `node <ZS>/tools/zsd.mjs lint <absolute path to DESIGN.md> --json` on a changed design file; correct format defects in the approved task area; record lint warnings that make a developer decision necessary; compare changed paths with the specified task; report the lint result and the unresolved items. The lint result includes selected document checks: it does not show interface accessibility.
7. **Record** `design_brief` (path, selections, unresolved and proposed items) and `design_file` (path, `x-zsd.kind`, review status, source method, unresolved items, lint result).

## Specifics

- **Format** (`design-format.md`; the profile for the rest): `version: alpha` and `x-zsd.profile: "0.1"`; a name and a short description; `colors`, `typography`, `spacing`, `rounded` and `components` for primary tokens, `x-zsd` for intent, sources, modes and other extensions. Uppercase hexadecimal colors, font weights as numbers, unitless line heights, pixel values for spacing and radius, token references for component colors; keep the necessary primary, surface, headline, body and label roles. One level 1 heading with the same text as `name`; the level 2 headings `Overview`, `Colors`, `Typography`, `Layout`, `Elevation & Depth`, `Shapes`, `Components`, `Do's and Don'ts` in this sequence, then `Motion`, `Iconography`, `Imagery`, `Accessibility` when applicable; other divisions in level 3 headings. Values only in YAML; functions, conditions and instructions in the body; token names in code format before each description; each component family a level 3 heading; each item of `Do's and Don'ts` starts with `Do` or `Do not`. Body 1,200 words or less, file 24 KiB or less.
- **Metadata**: `kind: project` for a project file; `source.method` is `authored`, `generated` or `hybrid`, with a source URL or source paths and the source date when applicable; `review.status: draft` until the specified inspection is completed, and the inspection date and area with `reviewed`. Do not mark unresolved design selections as approved. Keep the primary token source and component paths in `implementation`.
- **Source data** (`procedure.md`): record viewport, mode, route and state for interface measured data; keep measured values apart from estimates; a screenshot does not supply keyboard behavior or all component states. Open external sources only with developer approval for access.
- **Interface checks** (`procedure.md`): do not add or do tests unless the developer tells you to do tests, and do only the interface checks with developer approval. This governs checks and tests of the interface in this step.
- **One owner of the file.** This capability is the only one that writes the brief and `DESIGN.md`; it merges into an existing design file and never replaces one (`init` refuses to overwrite a file unless `--force` is supplied), and it writes no tokens file, theme file or `design-system/**/MASTER.md`. Recorded `aesthetic_direction`, `palette`, `typography`, `layout`, `constraints`, `design_tokens` and `component_inventory` are source data: record where each came from, and keep the status `proposed` for a value the developer did not confirm.
- A harness reads `DESIGN.md` only when its own instruction file points at it. `<ZS>/docs/template-guide.md`, "Connect a coding harness", gives the lines for `AGENTS.md`, `CLAUDE.md` and a Cursor rule: name them to the developer after the file is written; adding them is outside the specified task unless asked.
- Runtime dependency: Node.js 22 or later (`node --version`). The tool needs no npm installation and no service connection; the source gives no install method for Node.js.

## Checks

- **selections_sourced_or_proposed**: each selection has a source, a source location or an estimate label, or the status `proposed`; nothing unresolved is marked approved.
- **brief_separates_selections_from_examples**: the design brief divides the developer's selections from example values.
- **tokens_resolve**: tokens resolve without circular references and the file records the developer's selections.
- **estimates_and_missing_states_marked**: image readings are labelled estimates, and states and responsive conditions the source does not show are `unresolved`.
- **other_selections_kept**: only the specified data and its related instructions changed; for one area, only that area's data.
- **change_report_separates_specified_from_related**: the change report divides specified changes from related changes, and each changed selection has source data.
- **area_completion_met**: the area's own completion holds. Typography: each role has a function, and font families and weights agree with the supplied assets. Colour: each token has a function, and the report includes token contrast data and the accessibility inspection area. Layout: each breakpoint has a content condition, and the instructions include widths between the example viewports. States: each applicable state has a trigger and a result the user can see, and recovery steps and keyboard behavior are clear.
- **document_checks_reported**: the lint command ran on the changed file and the result shows the document check area and the unresolved items.
