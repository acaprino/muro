# HTML Deck (browser presentation)

Builds a presentation that is a web page: slides of a fixed size that fit any screen, moved with the keyboard. It is the browser alternative to `office-deck`, which produces a PowerPoint file; the user's wanted format decides between them. `<CD>` below stands for `<package_root>/scripts/claude-design-system-prompt/claude`.

## Behavior

0. **Read the originals first.** They are the method in the source's own words, and the steps below are an index into them. Read whole before working:
   - `<CD>/skills/make-a-deck.md`, the procedure of this capability (its Phase 1 to Phase 6);
   - `<CD>/skills/discovery-questions.md`, the protocol of the question round of step 1;
   - in `<CD>/system-prompt.md`, these chapters and only these: `# 2. Workflow`, `# 3. Asking questions first`, `# 4. Rooting designs in existing context`, `# 5. Content principles — no filler`, `# 6. Aesthetic principles — purposeful visuals`, `# 7. Visual hierarchy and rhythm`, `# 8. Typography system`, `# 9. Color system`, `# 14. Respecting the medium`, `# 17. Output principles`, `# 18. Collaboration and delivery` and `# 19. IP and content boundaries`. The lines before chapter 1, chapters 1, 10 to 13, 15, 16 and 20 and the `# Final principle` are not read for this capability.
   Where this body and an original differ, the original wins, except for the changes listed in the Sources section below under "Changes for coexistence".
1. **Brief (make-a-deck, Phase 1: Discovery; discovery-questions, Phases 1 to 5; chapter 3).** Read every attached resource before asking. "Confirm before building": "**audience** (determines tone and density); **format** (aspect ratio — 16:9 default — and slide count: a 10-minute deck is ~10 slides, a 30-minute one ~20–25); **tone** (formal corporate, casual internal, marketing-bold, technical); **source content** (read any PRD or existing material before sketching); **speaker notes** (off by default, only when explicitly requested); **brand / design system** (always confirm — if none, invoke `frontend-aesthetic-direction` before drawing)". That invocation is the `needs` on `aesthetic-direction` (step 2). The round is built and sized as discovery-questions Phases 2 and 3 say, asked once, as a structured form when the host has a question-form tool and otherwise in plain text; then the turn ends until the answers come back. "If the user gave enough context (e.g., "make a 5-slide deck for engineering all-hands from this PRD"), skip the question round."
2. **Take the look from what exists (chapter 4).** Use the recorded `aesthetic_direction`, `design_tokens`, or `palette`, `typography` and `constraints`; otherwise the user's brand material, read as chapter 4 says ("read the source — don't rely on memory"). With nothing to match, this step should have followed `aesthetic-direction` (see `needs`); if it did not, do as chapter 4 says: "If you cannot find context, **ask the user for it.** Do not invent a brand or visual language out of thin air unless explicitly asked to".
3. **Plan the layout system (make-a-deck, Phase 2; chapter 2, item 3).** "Before building any slide, commit to a layout system and vocalize it in a comment block at the top of the file. A typical deck has 4–6 layout types: cover/title, section header (full-bleed color or image), content slide (headline + chart/image/list), quote/pull-out, comparison/two-column, closing/CTA. For each: background treatment, headline size and position, body content area, footer (page number, brand mark, none)." "Limit the deck to **1–2 background colors**; section headers may break to a third, no more."
4. **Write the shell once (make-a-deck, Phase 3; chapter 14, "Fixed-size content scales itself" and "Persist state where it matters").** The source copies a deck-shell starter of its own host; it is not packaged, so this step writes a shell that does what the source says the starter handles: "scaling/letterboxing, keyboard and tap navigation, the slide counter, localStorage persistence, print-to-PDF". Each slide is one `<section>`, a direct child of the stage element of the fixed slide size. "Give each slide a `data-screen-label` so the user can reference it by name when commenting (`<section data-screen-label="01 Title">`). **Labels are 1-indexed** to match the slide counter the user sees."
5. **Build slide by slide (make-a-deck, Phase 4; chapters 5 to 9).** "Build in order, and show the user the file after 1–2 slides — don't perfect 15 in private and then reveal. Per slide:"
   - "**Type.** Body never under 24px on a 1920×1080 canvas, ideally 32px+; headlines 60–96px+."
   - "**Hierarchy.** One primary message per slide; supporting elements smaller and more muted."
   - "**Imagery.** From the design system, or honest placeholders (striped background, monospace label). No hand-drawn SVG filler."
   - "**No filler slides.** "Why choose us?" / "About this deck" cost the user attention — cut them."
   - "**Charts.** Show what matters; cut columns and data points that don't support the slide's point."
   - "Use the design system's spacing and color tokens — no new values inline."
6. **Speaker notes, only if requested (make-a-deck, Phase 5).** "When asked: add a `<script type="application/json" id="speaker-notes">` array in the head, one entry per slide, written as full conversational scripts (not bullet outlines). Slides with notes can carry less on-screen text." The source's starter renders them automatically; the shell of step 4 must render them itself, and the report says how they are shown.
7. **Verify and deliver (make-a-deck, Phase 6; chapter 18).** "Walk the deck top to bottom in the preview: scaling at multiple viewport sizes, counter increments correctly, keyboard nav (arrows, space) works, nothing overflows slide bounds, type meets the 24px+ minimum, contrast passes WCAG". Because the shell is written here, also check tap navigation, the position after a reload and the print layout. Without a browser, record each of these as not tested (chapter 18: "If you can't verify a UI behavior (no browser, no test data, an external dependency you can't reach), say so. Don't claim success on unverified work.").
8. **Record** `html_deck_plan` (layout system and slide list), `html_deck_file` and `html_deck_review`: what was walked and, as the source's summary asks, "caveats (e.g., placeholder imagery still needed), next steps (e.g., real charts to swap in), and decisions the user should sign off on".

## Specifics

- **No filler (chapter 5).** "**Every element must earn its place.**" What counts as filler, including "Made-up stats ("47% of users")", and the five-question test are in the chapter. "If you think additional sections, copy, or content would improve the design, **ask the user first.**" Figures, names and quotes come from the user's material; a value that is still missing is an honest placeholder, labelled as one.
- **The shell is written here.** The source says "Don't hand-roll the scaling — use the deck shell starter"; that starter is not in the selected snapshot, so step 4 writes the shell and step 7 must check it. The starter's `data-om-validate` tagging belongs to the source's host and is not used.
- The opening of the prompt says: "Avoid web-design tropes and conventions unless you are actually making a web page."
- Contrast and colour: step 7 checks that "contrast passes WCAG"; the minimums, from the prompt's `## Contrast (WCAG)` list in chapter 10, are "Normal text (under 18px): minimum **4.5:1** contrast ratio", "Large text (18px+ bold or 24px+): minimum **3:1**" and "UI components (buttons, icons): minimum **3:1**". Chapter 9 says "**Don't rely on color alone to communicate state.**" The thorough accessibility audit the source invokes at this point is the `design-review` capability, in its own step.
- "a single HTML file" (make-a-deck, first line).
- Variations of the deck and live tweak controls, when the user asks for them in the brief, are the `design-options` capability in its own step: record the request in `html_deck_review`. This step builds one deck.
- A company's distinctive UI patterns or branded visual elements are not recreated unless the user states the brand is their own (chapter 19, with the change recorded under Sources).

## Checks

- **layout_system_stated**: the file opens with the layout types and their rules, and every slide uses one of them.
- **slides_scale_and_navigate**: the deck letterboxes at different window sizes, the keys and the counter work and the position survives a reload; without a browser this is recorded as not tested.
- **slide_type_minimums_met**: no body text under 24px on the 1920×1080 canvas, and nothing overflows a slide.
- **no_filler_slides**: every slide carries one message the audience needs; none repeats another.
- **deck_content_from_material**: figures, names and quotes trace to the user's material; placeholders are labelled.
- **deck_walked_or_disclosed**: the deck was walked from first to last slide, or the report says what was not checked.
