# Muro desktop: harness manager, plugin sync and updater

The desktop app is one window with three tabs, **Sync**, **Activity** and **Settings**. Until Muro manages a harness, three steps take the place of the tabs (the first run). The README shows the pages with demo data.

## The pages

**First run.** Shown while no harness is managed, and until you finish it. When no harness can be ticked, **Set up later** closes it for the session. Step 1 lists the coding agents Mukade found on this computer, with the folder where each keeps its plugin configuration; nothing is ticked for you, and **Continue** saves the ones you tick and reads what they have installed. Step 2 lists the plugins already installed on them; the ones you keep become your plugin list, and each stays the installation it is: Muro binds it to its list entry, so the first sync installs nothing beside it. Step 3 has two switches, **Automatic sync** and **Start Muro when Windows starts**, both offered on; **Finish** saves them and opens Sync. A harness that cannot take plugins is listed and cannot be ticked.

**Sync** answers "is everything in line?" in one place. Rows are your plugins and columns are your harnesses.

- The strip on top is the sync state and is always visible: **Not checked yet**, **N changes ready to apply**, **Some plugins are not ready**, **<harness> cannot be read**, **N sources could not be checked** or **Everything is in sync**, with *Last check*, *Last sync* and *Next check* (or *Automatic sync off*). It counts the plan this window made, and with none it shows the check Muro recorded for the registry as it is now, with the time of that check, so a window opened after the background worker checked says what the worker found; **Review** and **Apply all** are offered then too, and each makes a fresh plan before it shows or does anything. The app-bar button and the tab badge say the same. **Check now** resolves every plugin's source and compares the list with what is installed; **Review** opens the plan; **Apply all N changes** applies it. A source that could not be resolved (offline, the repository gone, a rate limit) is never reported as in sync: the strip names how many, and **Check now** tries again.
- A plugin row shows its name and source, its latest version with the update policy, and one cell per harness: the installed version, or the change a sync would make there (Install, Update, Reinstall, Activate, Remove), No version, Paused or Unknown. A row opens the plugin dialog: its source, harnesses, update policy, custom instructions folder and prepared builds, and under **More** Check for updates, Adapt with AI, Plan a reinstall, Open instructions folder and Remove from my list.
- A column header opens the harness sheet: name, configuration folder, executable, whether to keep it in sync (off pauses it), the rule for plugins outside the list on this harness, what is installed there with **Add to my list** (which takes the installation over: the list entry is bound to the copy that is there, so the next sync leaves it alone, or updates it when it differs from the build, and never installs a second one beside it), and **Stop managing**. Under the name the column says **In sync**, **Paused**, **Sync N changes** (which opens the plan of that harness alone), that it cannot be read, or **Check to see the changes** (the recorded check says changes are waiting and no plan of this window shows where), and when it was last checked.
- **Add harness** lists what Mukade found on this computer and also takes one by hand. **Installed, not in your list** shows what a harness holds that your list does not, with the one rule for all of it (**Leave alone** or **Always uninstall**), each line saying what the rule does to it, and **Add to my list**.
- The review sheet lists every operation with its reason, and what is **Not ready yet** (a plugin without a build, a harness that cannot be read). With blockers it still applies what is ready and says how many items it left out.

**Activity** shows the AI adaptations that are running, each with its phase, log path and **Cancel**, then the events newest first. The filters are All, Sync (checks, syncs and the background worker's runs, a check that only looked included), AI adaptation and Problems (anything that failed, was cancelled or was interrupted). The background worker's last result appears there as an *Automatic sync* or *Background check* event. The log keeps the last 500 events.

**Settings** has five sections and no Save button: every change is saved as you make it. **Sync** holds the rule for plugins outside your list. **Background** holds Automatic sync, the check interval, Start Muro when Windows starts and Keep running when the window is closed. **Appearance** holds the theme. **AI adaptation** holds the agent, the Python command and the factory folder. **Maintenance** verifies the stored builds and cleans up the ones nothing uses.

When a plugin has no build for one of its harnesses, **Adapt with AI** rebuilds it with the factory, the harmonizer that also produces packages such as Marionette.

Windows-first native portable Tauri application. The Rust registry and desktop runtime live in `crates/`; the UI and native shell live in `apps/desktop/`. The Python factory remains independent and standard-library-only. The GUI communicates with bundled `tools/muroctl.exe` over correlated NDJSON; that backend invokes bundled `tools/mukade.exe` for discovery and executable resolution. Both tools can also be called directly. See [CLI reference](desktop-cli.md).

## Run from source

Requires Node/npm, Rust with the Windows build tools, Git and WebView2. Install dependencies with `npm ci`. Stage the private Python/factory resources into a **new** directory:

```powershell
python scripts/desktop_resources.py --out apps/desktop/src-tauri/resources
npm run desktop
```

The resource command verifies the official embedded Python archive hash and refuses to replace an existing directory; `--archive` takes an already downloaded copy of that archive for an offline build. The staged `factory/` is a copy of `muro/`, `prompts/` and the ADRs, and AI adaptation in the app runs that copy. When the factory changes, stage to a new directory and swap it in place of `apps/desktop/src-tauri/resources`; a stale copy runs the old factory. Build the CLI tools with `cargo build -p muro-desktop-runtime --bins` before launching the app. `npm run build` builds the frontend, `cargo build -p muro-desktop --features custom-protocol` embeds it in a native development executable (the one the packaging command below expects; a debug build keeps a console window). `npm run desktop:build` builds the optimized executable without publishing or installing it.

For an optimized production folder in one step, run `build-release.bat` from the repository root. It runs `npm ci` when `node_modules` is missing (or with `--ci`), stages fresh resources and tools under `.scratch\release`, builds release executables, fetches the Mukade license at the revision pinned in `crates/muro-desktop-runtime/Cargo.toml`, writes the portable folder to `release\` (made again on every build), installs it into `D:\Software\Muro` and removes the staging; cargo's `target\` stays as the build cache. The install copies over the folder: `data\` and anything else only the install holds stay, and it waits while Muro runs from there. `--no-install` stops at `release\`, `--target <folder>` installs elsewhere, `--jobs N` limits parallel Rust jobs. It does not publish, sign or zip the folder. Shinatama, Mukade and Xiox have the same script with the same steps and options.

To prepare a complete portable folder by hand, use fresh output paths:

```powershell
python scripts/desktop_tools.py --out .scratch/portable-tools
Copy-Item target/debug/muroctl.exe,target/debug/mukade.exe .scratch/portable-tools/
Invoke-WebRequest -Uri https://raw.githubusercontent.com/acaprino/mukade/02baf4fa1f269380fce8b84ccb5a2dbca8676907/LICENSE -OutFile .scratch/portable-tools/Mukade-LICENSE.txt
python scripts/desktop_package.py --exe target/debug/muro-desktop.exe --resources apps/desktop/src-tauri/resources --tools .scratch/portable-tools --mukade-license .scratch/portable-tools/Mukade-LICENSE.txt --out .scratch/Muro-portable
```

The tools script verifies the official Git and curl archive hashes, retaining licenses and runtime files. The Mukade license command fetches the license from the exact revision pinned in `crates/muro-desktop-runtime/Cargo.toml`; update both together when repinning Mukade. `--mukade-license` is required and the packager copies that file to `LICENSES/Mukade-LICENSE.txt`. The package includes the application, CLI executables, private resources, documentation, examples and SHA-256 manifest. It requires Windows WebView2; managed AI harnesses remain their own installed applications. Move the whole folder, not just `Muro.exe`.

## Registry workflow

1. Choose the harnesses to manage: in the first run, or with **Add harness** in Sync. Muro finds the executables with Mukade; each instance's configuration root is explicit, and a discovered session store is not a plugin root.
2. **Add plugin**: give its source, tick its harnesses and choose its update policy. **Check now** (or **Check for updates** in the plugin dialog) resolves the source to inspect native distributions and record the upstream revision. Prepared local distributions can also be entered directly, under Advanced.
3. If a distribution is missing, start an AI adaptation job. A real Claude Code agent performs intake and harmonization; the factory independently validates, checks sources and stages the output. Status and log paths appear in Activity. It does not install the generated package.
4. **Check now** calculates the plan, **Review** shows it and **Apply all** applies it. Applying verifies registry revision, observed inventory and artifact content again. A second plan after a successful sync has no operations. A plan with blockers (a plugin without a build, a harness that cannot be read) applies what is ready and leaves the blocked items out, when the review sheet's **Apply** or the background worker asks for it; without that request the service refuses the whole plan. On a harness that has a blocker nothing is uninstalled, because a plugin of your list whose build failed must not be removed as if it were outside the list.
5. **Always uninstall** (Settings → Sync for every harness, or in a harness's own sheet) includes recognized installed plugins outside your list in removals. This does not authorize deleting sessions or arbitrary configuration files. All replacement artifacts are prepared before operations begin; incomplete inventory blocks application.

Upstream version/revision and each native or Muro-generated distribution version are shown separately. Changing a plugin's source clears every prepared distribution and its resolved upstream metadata; resolve or adapt the new source before syncing. Editing only a name preserves existing provenance. Stable resolution prefers published GitHub releases; explicit pins and HEAD are available. Sources without sufficient release information require an explicit choice instead of a guessed version.

Registry writes are revision-checked and atomic; native operations have a journal and are followed by an inventory scan. Failed or interrupted operations require inspection and a fresh plan, not blind replay. Reinstall is an explicit plan operation that uses the retained verified artifact, not today's source. After it, the installed files must hash like that artifact on Claude Code, OpenCode and Pi; Codex reports no install folder and Hermes installs a Git clone, so there only the version and activation are checked. Maintenance verifies stored artifacts and removes artifacts no installation receipt references; plans calculated before a cleanup must be recalculated.

## Custom instructions from Markdown

Each registry plugin can have its own folder of custom instructions. These files are inputs to AI harmonization, alongside the selected upstream source. Write ordinary UTF-8 Markdown; no frontmatter, special filename or domain taxonomy is required. Nested folders and `.md` files are supported. Names and alphabetical order do not determine rule priority or activation.

1. Open the plugin (a row of the Sync table) and choose **More → Open instructions folder**. Muro creates and opens its managed folder under `data/custom-instructions/<plugin-id>/`. To use an existing folder, enter its absolute path in **Custom instructions folder** under **Advanced**, and save. Leave the field blank to return to the managed folder.
2. Create or edit one or more Markdown files with your editor. For example, put the following in `recap-adhd.md`: `During long operations, agent waits, important changes and autonomous decisions, give a short ADHD progress recap: where we are and what remains.`
3. Click **Reload files** under **Custom instructions** in the plugin dialog to reread the folder. It shows the folder, the Markdown files and the harnesses that need a new adaptation (*Instructions changed. Adapt again for…*). Adding, editing, renaming or removing a file can require regeneration; deleting the final file also requires removing its old contribution from the package.
4. Choose **More → Adapt with AI** for the destination harness. The agent reads a snapshot of the Markdown, decides how it becomes session policy, capability instructions or supported hooks, and records its reasoning and coexistence decisions. The job does not install the generated adapter. Changed files during the job prevent the old result from being accepted as current.
5. Review and apply a new synchronization plan. An artifact that does not match the current instructions is blocked, including a native distribution that has not incorporated them. Repeat adaptation for each destination harness that needs a new distribution.

The original files stay separate from upstream snapshots and survive source updates. Instructions are not automatically made permanent: that is an AI decision. Generated packages retain the original files needed at runtime and record the contribution of files carried entirely into policy. Read [the CLI workflow](desktop-cli.md) to inspect or open these folders and launch the same adaptation without the GUI.

## Runtime and storage

Portable distributions contain `portable.marker` and keep state under `data/` beside `Muro.exe`. Development builds without the marker use the application data directory for `dev.muro.registry`. `MURO_DATA_DIR` or CLI `--data` selects an explicit registry. External harness target roots stay explicit and are not moved with the app. The app always uses its own WebView2 profile, avoiding collisions with a parent application such as Shinatama.

**Sync state.** `data/sync-status.json` records when the registry last compared the installed plugins with your list and when it last brought a harness in line: `last_check`, `last_sync`, the number of operations and blockers of the last full plan with the registry revision that plan was made for, `errors` (the sources the last check could not resolve, `null` before any check), and the same two times for each harness (`checked`, `synced`). A file that cannot be read counts as no record, and the next check writes it again. A plan or a check writes the first part, an apply the second. Every snapshot carries it as `sync`, so the tray reads it, and the page shows its times, without a new inventory scan. A change to the list or to a harness makes it stale; a settings save keeps it current, because a setting does not change what a sync would do. The changes in the table cells come from the snapshot, or from a plan, which the page makes when you press **Check now** and again after a change. The counts in the strip come from that plan, or, while the window holds none for the registry as it is, from this record when its revision is the registry's: a window that has just opened shows what the background worker found, in step with the tray, and reads *Not checked yet* only when nothing was recorded for the registry as it is (a change to the list since, or no check yet). The record gives counts and not a breakdown, and it does not say which harness the changes are on, so a column with nothing of its own to show says *Check to see the changes* rather than *In sync*. `data/automation-status.json` holds the last result of the background worker, which Activity shows.

**Start with Windows.** Settings → Background → *Start Muro when Windows starts* writes a per-user Run value, `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, named `Muro`, holding `"<path of Muro.exe>" --background`. It is written with `reg.exe`, needs no administrator rights, and the key itself is the state. Turning it on also turns automatic sync on when it was off, since a start that syncs nothing is no use; turning it off leaves automatic sync as it is. At every start Muro repairs the value only when it names an executable that no longer exists (a portable folder that was moved); a value that names another copy of Muro that is still there is left alone, so a development build never takes over an installed copy's. `MURO_AUTOSTART_NAME` changes the value's name; the tests use it so they never touch `Muro`.

**`--background`.** Muro starts in the notification area and shows no window. Without the flag the window shows once the backend answers.

**Closing.** Closing the window hides it and Muro keeps running in the notification area, unless *Keep running when the window is closed* (`close_to_tray`) is off: then closing quits Muro, and nothing syncs until it is opened again. The tray icon has a state line (*In sync · checked 09:41*, *2 changes waiting · checked 09:41*, *Needs attention* when only blockers or sources that could not be checked are left, or *Not checked yet*), **Open Muro**, **Sync now**, **Pause automatic sync** (or **Resume**) and **Quit Muro**. **Sync now** checks and applies, whether or not automatic sync is on.

**One Muro for each data directory.** A second launch (the Start menu while Muro waits in the tray, or the Run value after a manual start) asks the running one to show its window and ends at once with exit code 0 and no output; with `--background` it ends without showing anything. The running Muro holds a named Windows object, `Local\MuroShow-<hash of the data directory>`, which belongs to the user's session and disappears with the process. A different data directory (`MURO_DATA_DIR`) is a different Muro with its own backend. Every build without `portable.marker` (a development build, for one) uses the same default data directory, `%APPDATA%\dev.muro.registry`, so those count as one Muro; a portable folder keeps its own `data/` and is another Muro.

**Quit.** **Quit Muro** in the tray, and a close with `close_to_tray` off, start no new sync, wait up to 60 seconds for the one in progress while the state line reads *Finishing the sync…*, and then exit. A sync that lasts longer is cut off at that point. `sync_now` and `apply` wait this way, whoever started them, window or tray; a settings save or another short write started from the window can still be cut by a quit. A close with `close_to_tray` off quits even while a sync holds the registry: the shell reads the setting from the registry's lock-free `status` and keeps the last value it read for when that cannot be read.

**The background worker.** While Muro runs, including in the notification area, a worker does a sync at start and then at every interval (Settings → Background, default 60 minutes; the setting is read again every few seconds, so a change takes effect within seconds). Every pass it resolves every plugin's source, reads every managed harness and records the result for the tray and the Sync page, so they say the truth also when automatic sync is off. A pass that could not resolve a source is recorded as failed, with the names of the plugins (*Sources not checked: …*), and the tray reads *Needs attention*; what could be applied still is.

**The window beside the worker.** The worker and the tray's **Pause** change the registry while the window is open or hidden. The window reads the registry again when it gets the focus (it is shown again from the tray, or clicked back to) and every 30 seconds while it has the focus, and only when nothing of yours is under way: no request running, no dialog open, no text box being typed in. It asks for no plan on the way: the recorded check says what changed. A settings save that the registry refuses because it moved (*Registry revision changed*) reads the registry again and sends the same change once more, over what the worker saved; only a second refusal reaches you.

**Waiting for the registry.** The registry takes its writer lock without waiting and refuses a second request, and a check of sources that answer slowly holds it for as long as they take. The desktop shell does the waiting for every page, in one place: a request of the window waits for the sync in progress (10 minutes at most), then tries a busy registry again every 250 ms for 15 seconds before it returns the error. The tray and the worker read the lock-free `status` instead of a snapshot. A launch while another process holds the registry waits for it too.

- **Automatic sync on:** it then applies the plan without a review step. Blockers do not stop it: it applies what is ready and leaves the blocked items out, and the event says what was left out (Activity: *Automatic sync*, failed when blockers remain). On a harness that has a blocker nothing is uninstalled, even with *Always uninstall*.
- **Automatic sync off:** it only checks. Nothing is installed or removed; the tray says how many changes are waiting (Activity: *Background check*).

One sync runs at a time, whoever asks: the worker, the tray's **Sync now** or a request.

For diagnostics, `Muro.exe --request ACTION '<json>'` runs one request through the bundled `muroctl` and prints the result without opening a window (the windowed release build has no console, so prefer `tools\muroctl.exe` for scripts). The actions are listed in [the CLI reference](desktop-cli.md#request-actions). `autostart` and `set_autostart` are answered by the window's shell only, not by `muroctl`. Moving the portable folder rebases registry, receipt and plan paths inside it at the next start.

Claude Code, Codex, OpenCode, Pi and Hermes have separate installation contracts. DeepSeek is discoverable through Mukade but has no Muro plugin adapter. An unavailable command or failed inventory is shown as incomplete, never as an empty installation. Existing host permissions remain authoritative.

AI adaptation currently requires Claude Code for its budgeted execution. Codex does not expose an equivalent dollar-budget flag, so the app does not pretend to enforce one. Claude's budget is checked by the host between turns, not a strict prepaid ceiling. Jobs also have a 30-minute deadline. On Windows their subprocess trees are attached to a kill-on-close job object. Cancellation leaves the registry unchanged unless validated output has already been recorded. Native install commands can have host-specific effects; inspect the plan and resulting activity.

## Theme

The interface has one look. Settings → Appearance chooses its theme: **System** (the default, follows Windows), **Light** or **Dark**. The choice is remembered in the WebView's own storage (`muro.theme`); `apps/desktop/src/look.ts` sets the resolved `data-theme` on the root and `apps/desktop/src/styles.css` holds both palettes. The window is acrylic (`transparent` and `windowEffects` in `tauri.conf.json`): the ground thins so it shows through the bars and sheets, and the title bar follows the theme. Maintenance (verify, reinstall, clean up) is a section of Settings.

## Verification

AI work-directory and read-only-factory instructions are agent rules, not an OS filesystem sandbox. Windows process jobs enforce child-process lifetime only; host permissions remain authoritative. Generated manifests must match the resolved upstream revision before their distributions are recorded.

```powershell
cargo test -p muro-registry -p muro-desktop-runtime
npm test
npx tsc --noEmit
npm run build
node apps/desktop/tests/browser.mjs   # MURO_UI_PORT=<port> when 1422 is taken
node apps/desktop/tests/screenshots.mjs   # the README screenshots, from demo data
cargo build -p muro-desktop-runtime --bins
cargo build -p muro-desktop --features custom-protocol   # embeds the frontend `npm run build` made
node apps/desktop/tests/native.mjs   # MURO_CDP_PORT=<port> when 9227 is taken
node apps/desktop/tests/native-shell.mjs   # MURO_CDP_PORT=<port> when 9228 is taken
python muro_build.py --manifest examples/marionette/sources.json --validate
```

The full Python suite (`python -m pytest -q`) runs in the Tests workflow on GitHub; so do the Rust tests, `npm test`, the type check, the frontend build and the browser tests of the `desktop` job.

- **`npm test`** runs Node's test runner over `apps/desktop/tests/*.test.ts`: the model, the forms and sheets, Settings and Activity, the first run and the request queue, as HTML strings and plain functions.
- **`browser-*.mjs`** (sync, harness, settings and setup; `browser.mjs` runs them one after the other) start the Vite dev server and headless Edge (Playwright's `msedge` channel) and drive the real interface against `fake-transport.js`, a fake of the registry service that keeps its rules: revision conflicts, blockers, `allow_blocked`, removals only on a harness without a blocker. They prove the interface, not the service.
- **`native.mjs`** drives the real executable over the WebView2 debugging port, against the real Tauri `request` command, the real registry service and a real OpenCode profile in a temporary folder. Mukade finds that profile because `XDG_CONFIG_HOME` points there, so the first run picks the harness as anyone does, and the other harnesses of the computer are listed and left alone. Then a plugin is added, Check now shows the change, Apply all installs it into the profile, the settings already in `opencode.json` stay, the table shows the installed version, and a second Check finds everything in sync with its times moved. It also saves a setting on change. It uses a Run value of its own name and deletes it.
- **`native-shell.mjs`** drives the same executable but calls the shell's `request` command from the page, not the interface: start with Windows, close to the tray, `--background`, the worker, a second launch and the quit path. It asks the window to close the way Windows does (`WM_CLOSE`) and reads whether the window shows from user32. The tray menu itself is a native menu that no test reaches.

The two native tests prove the app/configuration boundary; they do not prove that an OpenCode agent loaded and executed a plugin, and none of them is a real sign-in to Windows. See the dated verification record for real host checks and remaining limits. No personal harness installation is required by these tests.
