# EGM live on Claude Code — 2026-11-14

First live execution of EGM capabilities end to end, after the intake
(`2026-11-14-egm-intake.md`) and the focused-index runs
(`2026-11-14-focused-index-by-entry.md`), whose session 7 had only shown the host
reading EGM files without executing a step.

## Setup

- Host: Claude Code 2.1.325 in a cloud container (not the owner's machine of the
  earlier records), CLI authenticated, model `sonnet`, package alone
  (`--setting-sources project,local --strict-mcp-config`).
- Recipe flags as in AGENTS.md; `--allowedTools` extended per session so the step's
  declared tools exist: `"Skill" "Read" "Write" "Edit" "Glob" "Grep"` for the drift
  sessions, plus `"Task"` for the review session. Budget `--max-budget-usd 2`,
  raised to 4 for the review session because the staged flow spawns up to nine
  subagents. Sessions one at a time; session folders under `~/.claude/projects/`
  were left behind despite `--no-session-persistence` and deleted after each run.
- Test project (scratch, outside the repository): `docs/designs/rate-limiter.md`
  describing a `RateLimiter` with `burst_allowance`, caller-set `window_seconds`
  and Redis persistence; `src/ratelimiter.py` implementing none of those, with a
  hardcoded 60-second window and an undocumented `_blocklist` — one planted drift
  of each of the four kinds the source names. `docs/designs/logging.md` matches
  `src/logging_util.py` exactly, as the no-drift control.
- Sample size: one session per row below. Requests in Italian, mirroring the
  wording class of `eval-cases.json` (`egm-design-drift`, `egm-fresh-review`).

## Finding and fix: the direct output handoff did not happen

In session 1 the host ended with "Bash mi è stato negato, quindi non ho registrato
l'output" — wrong twice: the only denial was the `cat` loop, and the launcher had
just succeeded twice. The direct result gave it nothing to push back with: unlike a
mapped step (`submit`, `scope`, "submit this step first"), it carried only
`required_outputs`, and the skill phrased the direct `record` as something to do
"to keep its outputs for a follow-up turn".

Two changes, each run live before being kept (ADR-0015):

1. `muro/runtime.py`: a `direct` result now carries the exact handoff line as
   `submit` (`record --project … --direct --capability <id> --outputs
   "<state>/outputs.json"`), mirroring the mapped step's field. Session 3 showed
   the line alone is half-followed: outputs written, command skipped.
2. `muro/adapters.py` (workflow text of every host's skill): the direct handoff is
   now imperative — run the returned `submit` line before answering — and states
   that a denied shell command does not deny the launcher. Session 4 followed it,
   through the same denial that stopped session 1.

Per-task cost of the safeguard: one line more in each direct result and one
launcher call per direct step (~2 s, no denial observed). Tests updated:
`test_direct_steps_carry_no_map_submission` now asserts the direct `submit` is the
`record --direct` line and nothing of the mapped flow (`map_id`,
`remaining_steps`, `scope`, `--map-id`) travels with it.

## What the runs show, and what they do not

- Both EGM execution shapes ran end to end on a live host: a direct step
  (`design-drift`) with its output recorded, and a mapped, resumable step
  (`fresh-review`) through confirm, fresh-subagent reviewers, atomic submission
  with per-intent checks and `complete`. The evidence rules of ADR-0018 held
  unprompted: the host used `not-applicable` with the declared conditions and
  stated an isolation limit inside a `pass` evidence rather than hiding it.
- The drift step's findings were exactly the planted set, twice (sessions 1 and
  4), with no false positive on the control document — a content result, not only
  mechanics, but on a 2-document toy project.
- The staged review honored the preset named in the request (no gate shown), ran
  stages sequentially and skipped stage 9 with the reason. Whether the gates work
  interactively was not tested: `-p` sessions cannot answer them.
- One session per configuration, one model (Sonnet 5.5 on a small context), one
  host. Not run live: concept-brief, design-doc, the review loop, finding
  resolution, codebase-contracts; the other four hosts (their skill text changed
  identically in `adapters.py`; only unit tests cover them); a document with an
  implementation plan (stage 9 and the range split); resume of the review map.
