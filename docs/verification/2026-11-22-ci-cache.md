# CI: reuse the build already in cache (2026-11-22)

Owner instruction: use the build already in cache so that cargo, tauri and the other components are not rebuilt from
scratch on every run, and do not run the same verification twice for one commit.

## What was measured first (read-only, `gh run view`)

- `Tests`, job `desktop`, a run with an exact cache hit (45017469503, develop): cache restore 29 s, Rust tests 54 s,
  Frontend unit tests 27 s, Shell tests 8 s, Browser tests 399 s; the job took 9 min 1 s. A run without a hit costs about
  190 s more (Rust tests 113 s, Shell tests 139 s). The browser tests (node, vite and Edge, no Rust) are the largest
  step and nothing in this change shortens them.
- `Release` (44969540468, main): job 10 min 10 s, of which "Prepare and build" 9 min 15 s (`npm ci`, the release builds
  of the runtime tools, mukade and the tauri shell, packaging inputs). No cache was used.
- The repository's Actions cache is at 10.5 GB of its 10 GB, in 31 entries: sixteen are `desktop-Windows-<hash of
  Cargo.lock>` (189 to 655 MB, 9.9 GB together), saved once for each ref that ran (develop, main and `refs/pull/<n>/merge`
  of the release pull requests), and fifteen are npm caches of 34 to 41 MB (0.6 GB), the same way. The old key had no restore key and no
  compiler in it.
- Branch `main` has no protection and no ruleset (`gh api`: 404 and an empty list), so the release pull request has no
  required check that its run would feed.

## What is cached

| Where | Paths | Key | Restore keys | Saved |
|---|---|---|---|---|
| `tests.yml` `desktop` | `~/.cargo/registry/index`, `~/.cargo/registry/cache`, `~/.cargo/git/db`, `target` | `<os>-cargo-desktop-v1-<rustc>-<hash of Cargo.lock>` | `<os>-cargo-desktop-v1-<rustc>-` | Last step, when there was no exact hit and the Rust tests and the Shell tests passed, whatever the later steps did |
| `release.yml` `release` (on `main`) | the same four paths | `<os>-cargo-release-v1-<rustc>-<hash of Cargo.lock>` | `<os>-cargo-release-v1-<rustc>-` | The action's post step, when the whole job succeeds |
| `release.yml` `release` | the npm cache (`cache: npm` on `setup-node`) | the action's own, on `package-lock.json` | | By the action |
| `tests.yml` `desktop` | the npm cache (already there) | the action's own | | By the action |

`<rustc>` is `rustc --version` with every run of other characters turned into `-`; a new compiler starts a new cache
(the artifacts of another compiler are useless), and `v1` is bumped to start over if a restored chain grows too big.
Both jobs set `CARGO_INCREMENTAL=0`. The restore and save of the `desktop` job are the same action as before
(`actions/cache` at the SHA already in the repository: its `restore` and `save` entry points, checked at that commit), so no
new action is introduced. The debug build and the release build have different keys, because their artifacts differ.

Not cached, and why: Playwright browsers (the browser tests use the Edge of the runner image through the `msedge`
channel, nothing is downloaded); pip (the Python jobs install only `pytest`, there is no requirements file for
`setup-python` to key on: its cache would hold a few megabytes); Inno Setup (the step finds it installed, 0 s in the last
run); the Python, MinGit and curl archives of the release (a few tens of megabytes, checked against pinned digests; a cache
would need a flag in the shared `build-release.bat`); the Marionette checks of `marionette.yml` (the pinned sources are
verified Git fetches and the project cache is trusted as written, so it is not carried between runs).

## What was removed

`Tests` no longer runs on `pull_request` and no longer on a push to any branch other than `develop`: it ran on the push to
develop, again on the develop -> main pull request (`refs/pull/<n>/merge`, the same tree) and again on the push to main,
each time with a Windows runner and its own copy of the 655 MB cache. It keeps `push` on `develop` and
`workflow_dispatch` (`gh workflow run tests.yml --ref <branch>`). `marionette.yml` keeps its own path-filtered `push` and
`pull_request`. `release.yml` is the gate of publication, as before: it builds and does not test, so the release pull
request should be merged when the run of develop's tip is green. AGENTS.md and the README say so.

## Estimated effect

- The warm run of `desktop` is what it was (about 9 min, the browser tests dominate); the gain is the cold run: a change
  of `Cargo.lock` or of the runner's compiler restores the newest cache of the same compiler and rebuilds only what
  changed, instead of the whole workspace (about 190 s saved on a lock change; a new compiler is a cold run, as it was).
- Two Windows runs per release are gone (the pull request and the push to main), about 18 minutes of runner time, and
  their two 655 MB cache copies.
- `Release`: the cargo release build is restored from main's own cache from the second release on, and `npm ci` reads the
  npm cache. I did not measure how much of the 9 min 15 s is cargo; I expect several minutes. The first release after this
  change, and the first after a lock or compiler change, is a cold run that fills the cache.

## Risks

- Cache size. The new entries are one debug `target` (about 650 MB, as the old one) on `develop` and one release `target`
  on `main` (not measured; with LTO and `strip` I expect 0.5 to 1 GB), plus the two npm caches. With no copy per pull
  request and per main push, the steady state is about 2 GB, well under the 10 GB. A restored chain keeps the artifacts of
  dependencies the lock no longer names, so each save can be a little larger than the last; `v1` is the reset.
- The new keys do not match the 16 old `desktop-Windows-*` entries (9.9 GB), which are
  now orphaned until GitHub evicts them (unused for 7 days, or least recently used above 10 GB): until then the repository
  stays at the limit and a new entry can evict one of the new ones. They can be deleted with `gh cache delete` (a write; not
  done here), after the first green run of the new `desktop` job.
- The first runs are cold: the first `Tests` on develop and the first `Release` on main after this change.
- A cache saved only after the two compiling steps passed, never from a failed compile; with an exact hit nothing is
  saved, so the workspace crates are rebuilt every run (a fresh checkout makes their files newer than the cached
  artifacts anyway) and only dependencies are reused.
- No required check on `main`, so removing the pull request run blocks nothing; if one is added for `Tests`, the release
  pull request would wait for it forever.
