# CI: reuse the build already in cache, as the standard of all the repositories (2026-11-22)

Owner instruction: use the build already in cache so that cargo, tauri and the other components are not rebuilt from
scratch on every run, and do not verify the same commit twice. Then: "non è che ognuno fa quello che vuole": the
workflows follow the CI standard that every repository follows (identical names, keys, triggers and wording), and this
repository's first version of the cache was changed to it.

## What was measured first (read-only, `gh run view`)

- `Tests`, job `desktop`, a run with an exact cache hit (45017469503, develop): cache restore 29 s, Rust tests 54 s,
  Frontend unit tests 27 s, Shell tests 8 s, Browser tests 399 s; the job took 9 min 1 s. A run without a hit costs about
  190 s more (Rust tests 113 s, Shell tests 139 s). The browser tests (node, vite and Edge, no Rust) are the largest step and
  nothing in this change shortens them.
- `Release` (44969540468, main): job 10 min 10 s, of which "Prepare and build" 9 min 15 s (`npm ci`, the release builds of the
  runtime tools, mukade and the tauri shell). No cache was used.
- The repository's Actions cache was at 10.5 GB of its 10 GB, in 31 entries: sixteen `desktop-Windows-<hash of Cargo.lock>`
  (189 to 655 MB, 9.9 GB together), saved once for each ref that ran (develop, main and `refs/pull/<n>/merge` of the release
  pull requests), and fifteen npm caches of 34 to 41 MB (0.6 GB). The old key had no restore key and no compiler in it.
- Branch `main` has no protection and no ruleset, so no required check depends on the pull request run.

## What the workflows are now (as the standard)

| | `tests.yml` | `release.yml` |
|---|---|---|
| Triggers | `push` to `develop`, `pull_request` to `develop`, `workflow_dispatch`; never the `develop` -> `main` pull request or `main` | `push` to `main`, `workflow_dispatch` (unchanged) |
| Env of the job that builds | `CARGO_INCREMENTAL: '0'` on `desktop` | `CARGO_INCREMENTAL: '0'` on `release` |
| Cache key (pwsh) | step `Cargo cache key` (`cargo-key`): the toolchain is `rustc -vV` release and commit hash; the lock part is a hash of the `source =` and `checksum =` lines of `Cargo.lock` only, so a release that rewrites the version of the workspace's own crates does not start a new cache | the same step |
| Cache | step `Restore the compiled Rust dependencies`, `actions/cache` at the SHA already in the repository: `~/.cargo/registry/index`, `~/.cargo/registry/cache`, `~/.cargo/git/db`, `target`; key `<os>-cargo-desktop-<toolchain>-<lock>`, restore key `<os>-cargo-desktop-<toolchain>-` | the same, purpose `release`: it runs on `main` and cannot read develop's caches, so its first run warms it |
| npm | `cache: npm` with `cache-dependency-path: package-lock.json` | none: the lock files carry the version the release rewrites, so the key could never hit |
| Playwright | not applicable: the browser tests use the Edge of the runner image (`msedge` channel), nothing is downloaded | not applicable |
| Tests of the release | | none: the gate is the `Tests` run on develop's tip, which is the same commit; the release workflow builds and publishes |

The cache is saved by the action's own post step, when the job succeeds and there was no exact hit; with no exact hit the
newest cache of the same toolchain is restored and cargo rebuilds only what the lock changed. The Python job (`tests`, Linux)
has no Rust and no cache: it installs only `pytest` and has no requirements file for `setup-python` to key on.
`marionette.yml` keeps its own path-filtered `push` and `pull_request` and is not part of the standard.

## Estimated effect

- The warm `desktop` run stays about 9 minutes (the browser tests dominate); the gain is the cold run: a change of
  `Cargo.lock` or of the compiler restores the newest cache of the same toolchain and rebuilds only what changed (about 190 s
  saved on a lock change; a new compiler is a cold run, as it was).
- Two Windows runs per release are gone (the pull request and the push to main), about 18 minutes of runner time, and their
  two 655 MB cache copies.
- `Release`: the cargo release build is restored from main's own cache from the second release on. I did not measure how much
  of the 9 min 15 s is cargo; I expect several minutes. The first release after this change, and the first after a lock or
  compiler change, is a cold run that fills the cache.

## Risks

- Cache size. The new entries are one debug `target` (about 650 MB, as the old one) on `develop` and one release `target` on
  `main` (not measured; with LTO and `strip` I expect 0.5 to 1 GB), plus the npm cache. With no copy per release pull request
  and per main push, the steady state is about 2 GB, well under the 10 GB. A restored chain keeps the artifacts of
  dependencies the lock no longer names, so a save can be a little larger than the last; the standard has no trim step.
- The new keys do not match the 16 old `desktop-Windows-*` entries (9.9 GB), which are now orphaned until GitHub evicts them
  (unused for 7 days, or least recently used above 10 GB): until then the repository stays at the limit and a new entry can
  evict one of the new ones. They can be deleted with `gh cache delete` (a write, not done here) after the first green run.
- The first runs are cold: the first `Tests` on develop and the first `Release` on main after this change.
- With an exact hit nothing is saved, so the workspace crates are rebuilt every run (a fresh checkout makes their files newer
  than the cached artifacts anyway) and only dependencies are reused.
